# SKILL · product-qa

## When to Use
기능 기획, 화면 문구, Android 변경안, 설치 안내 또는 광고 소재를 검수할 때.

## Procedure
1. 의뢰의 완료 조건과 기준 문서, 변경안 또는 제작물을 대조한다.
2. 정상 흐름과 대표 실패·취소·재시도 조건을 정리한다.
3. 항목별 확인 방법, 기대 결과, 증거, 결과 상태를 남긴다. 실제 기기가 필요한 항목에는 필요한 환경을 적는다.
4. 기준이 서로 충돌하면 문서 출처와 영향을 명시해 PM의 결정을 요청한다.

## Verification
- 각 결론에서 사용한 증거를 찾을 수 있는가?
- 기기나 외부 시스템 확인이 필요한 항목의 재현 방법이 있는가?
- 출시나 게시를 막는 조건과 담당자가 분명한가?

## Handoff
PM에게 검수 파일의 경로와 우선 처리할 사항을 넘긴다. 수정 요청에는 재현 절차와 수정 후 기대 결과를 포함한다.

## 실무 납품 검수

근거 귀속, 작업별 입력의 충분성, 사실과 가설의 구분, 후속 작업에 필요한 요약을 살핀다. 혼입된 트랙이나 확인되지 않은 조건이 있으면 ID와 고칠 문장을 특정한다. 구조화 검수에서는 받은 검수 대상만 판단하고, 납품을 막는 문제를 요청된 형식으로 남긴다.

실무 Markdown 납품의 `columns`는 각 항목에 들어갈 필드명이다. 제목과 필드 목록으로 렌더링된 산출물은 필드의 내용과 완결성을 검수한다. 의뢰의 산출물 이름에 붙은 '표'는 항목별 계획을 뜻한다.

선행 요약에서 확인한 설계는 선행 문서의 제안으로 표시할 수 있다. Markdown 파일 링크와 자료의 근거 ID를 구분하고, 제안의 실제 성과가 확인됐다고 서술하는지를 검수한다.
