# 시연 결과: 파비

## 무엇이 다른가

- **PM에게만 말하면 됩니다.** 요청을 정리하고, 직원을 배정하고, 결과를 모아 보고하는 일은 PM이 합니다. 사용자는 정리안을 승인하고 결과를 받습니다.
- **질문에 대한 답부터 받습니다.** PM이 요청에서 알고 싶은 질문을 뽑고, 모든 문서는 그 질문에 대한 답과 추천을 첫 줄에 씁니다. PM 보고도 판단, 맡긴 일, 결론부터 보여 줍니다.
- **근거를 지어낼 수 없습니다.** PM이 자료에서 뽑은 근거마다 원문 인용이 붙고, 인용이 실제 자료에 없으면 프로그램이 받아들이지 않습니다.
- **검수를 통과한 문서만 받습니다.** QA가 정리안, 배정, 문서를 각각 검수하고, 통과하지 못하면 결과를 만들지 않습니다.

## 1. PM에게 한 말

> 파비 관련 자료 보낼게. 파비는 두 가지 사업으로 진행하고 있는데 서로 별개니까 섞지 말고 따로 봐줘. 첫째, 정부지원사업: 외국인 K-pop 팬에게 한국어를 가르치는 교육 콘텐츠로 지원사업에 등록하려고 해. 지원사업을 받으려면 무엇이 필요한지 먼저 파악하고, 그에 맞게 교육 콘텐츠 방향을 디벨롭해줘. 둘째, 아리랑TV와 협업하는 AI 굿즈 판매: 파비를 많이 팔고 싶어. 앱이나 파비 로봇에 추가하면 좋을 기능이 있는지, 셀링 포인트를 뭘로 잡고 어떻게 팔아야 하는지 알려줘.

요청에 알고 싶은 것이 분명해서 PM은 따로 질문하지 않았습니다. 대신 세 가지를 직접 정하고 정리안에 적었습니다.

- 공식 신청서나 발표 자료가 아닌 내부 검토용 문서로 만든다.
- 지원사업의 대상 공고와 연도는 확정하지 않는다. 자료의 2026 공고 요약은 출발점으로만 쓰고 공식 원문 확인 항목을 남긴다.
- 문서별 마감은 자료만으로 정하지 않는다.

## 5. 결과

[PM 결과 보고](cases/pabi/outputs/README.md)를 열면 PM 정리, 질문별 답, 문서 목록이 차례로 나옵니다. 아래는 PM 정리의 앞부분입니다.

```text
## PM 정리

요청을 정부지원사업·한국어 교육 콘텐츠와 AI 굿즈 판매로 나눠 내부 검토했습니다.

### 아리랑TV 협업 AI 굿즈 판매

- 판단  매니저 방향은 선택됐지만 구체 동작과 자료 사용 권한은 미정이므로,
        앱에서 기능을 먼저 검증하고 판매 약속은 확인 가능한 범위로 제한했습니다.
- 맡긴 일  마케팅 (marketing) - AI 굿즈 판매를 위한 기능, 셀링 포인트, 판매 흐름의 우선순위를 제안한다.
- 결론  앱의 일정 알림을 먼저 검증한 뒤 반복 사용이 확인되면 로봇 연계를 검토하고,
        '팬의 일정을 챙기는 파비'를 셀링 포인트로 제안하되 권리나 파트너 조건이
        확인되지 않은 혜택은 판매 약속에서 제외합니다.
```

질문별 답은 다음과 같습니다.

| 질문 | PM 팀의 답 | 문서 |
| --- | --- | --- |
| 지원사업에 등록하려면 무엇이 필요한가? | 현재 자료로는 신청 자격을 확정할 수 없습니다. 해당 연도 공식 공고에서 신청 주체, 사업 목적, 제출 서류, 자부담, 일정을 먼저 대조할 것을 추천합니다. | [요건 확인표](cases/pabi/outputs/grant-requirements.md) |
| 교육 콘텐츠를 어떻게 발전시킬까? | "방송에서 접한 표현을 한국어로 말해 보고 파비와 짧게 대화하기"를 우선 후보로 추천합니다. 방송 원본이나 아티스트 음성 없이 학습 경험부터 시험합니다. | [교육 콘텐츠 검증안](cases/pabi/outputs/grant-concept.md) |
| 앱·로봇 기능, 셀링 포인트, 판매 방법은? | 앱의 매니저형 일정 알림을 1순위 기능으로 먼저 검증하고, 반복 사용이 확인되면 로봇과 연계합니다. 셀링 포인트는 "팬의 일정을 챙기는 파비"로 잡습니다. | [굿즈 기능·판매 우선순위안](cases/pabi/outputs/goods-strategy.md) |

PM이 사용자에게 남긴 결정 사항은 세 가지입니다.

- 검토할 지원사업의 공식 공고와 연도를 지정할지
- 아리랑 협업 범위와 아티스트·원곡 자료의 사용 권한을 확인할 수 있는지
- 매니저 방향을 어느 사업에 적용할지, 실물 형태를 지금 정할지

문서의 `[e-manager]` 같은 표시는 [근거 파일](cases/pabi/pm/evidence.toml)의 근거 번호입니다.

## 테스트

### 자동 테스트 33개

실제 모델 대신 정해진 답을 돌려주는 가짜 모델을 넣고, 프로그램이 규칙대로 움직이는지 확인합니다. 코드를 고칠 때마다 다시 돌려 기존 동작이 깨지지 않았는지 봅니다.

```bash
python3 -m unittest discover -s hermes/tests
```

| 확인하는 것 | 예 |
| --- | --- |
| 근거를 지어내지 못한다 | 원문에 없는 인용, 다른 파일을 출처로 단 인용을 거부한다. |
| 모든 질문에 답한다 | 답할 문서가 없는 질문이 있거나, 문서가 목록에 없는 질문에 답하면 정리안을 거부한다. 보고서는 질문별 답을 문서 목록보다 먼저 보여 준다. |
| PM 정리는 기록과 맞는다 | 보고서의 "맡긴 일"은 배정표에서 그대로 옮긴다. PM 정리 호출이 실패해도 검수를 통과한 문서는 전달한다. |
| 승인 없이는 진행하지 않는다 | 사용자가 `n`을 입력하면 아무것도 저장하지 않는다. 같은 이름의 기존 정리안을 덮어쓰지 않는다. |
| PM과 QA가 정해진 만큼만 고친다 | QA 의견이 있으면 PM이 한 번 고치고, 남은 의견은 승인 화면에 표시한다. 사용자의 수정 요청은 세 번까지 받는다. |
| 직원은 필요한 자료만 받는다 | 다른 사업의 근거나 배정되지 않은 근거, 앞 문서의 전문은 받지 않고 요약만 받는다. |
| 검수를 통과해야 결과가 나온다 | 검수를 끝내 통과하지 못하거나 배정 검수가 해결되지 않으면 결과 문서를 만들지 않는다. 수정할 때는 수정된 문서와 그 문서를 이어받은 문서만 다시 쓴다. |
| 모델 응답 형식을 확인한다 | 필드가 빠진 응답, 키가 중복된 응답, 완료 기록이 없는 모델 호출을 거부한다. |
