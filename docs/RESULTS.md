### 3. 잘 된 점
- **보고 → 배분 → 처리 → 반영**이 한 바퀴 돌았다. 클라이언트가 받은 버그 신고가 PM 칸반에 올라갔고, PM이 업무를 나눴고, 결과가 최종 칸반에 반영됐다.
- **모르는 것을 지어내지 않았다.** 문서에 없는 "공유 후 권한 변경 방법"은 FAQ에서 `[확인 필요]`로 남겼다.
- **잠정 일정을 확정처럼 쓰지 않았다.** FAQ에는 출시일을 넣지 않았고, 블로그에는 `[출시일 확정 후 기입]`으로 남겼다.
- **승인은 사람에게 남겼다.** 발송, 게시, 일정 확정은 하나도 없다.

### 4. 한계
- 팀원끼리 직접 보낸 handoff는 받는 쪽이 이미 일을 끝낸 뒤라 카드로 이어지지 않았다. 카드는 PM만 만들기 때문이다.
- 최종 칸반에 새로 생긴 할 일은 표에만 남는다. 다음 회차에 카드로 올려야 한다.
- 실행할 때마다 세부 내용은 조금씩 다르다. 카드 구성, 인젝션 격리, 승인 대기 같은 핵심 동작은 두 번의 실행에서 같았다.

## 프로젝트 결과

회의록·고객 메일·제품 자료를 바탕으로 **고객 응대 → PM 업무 배분 → 담당 에이전트 작업 → PM 최종 정리**가 이어지는 팀 워크플로를 구현했다.

- **업무 배분과 실행.** PM 에이전트가 후속 작업을 칸반 카드로 만들고, Hermes가 카드의 선후 관계에 맞춰 담당 에이전트를 실행한다.
- **검토 가능한 산출물.** 고객 메일 분류와 답장, FAQ, 출시 블로그, 제휴 검토 초안과 최종 칸반을 Markdown으로 남긴다. 보드 기록에서 담당자와 업무 인계 내용을 확인할 수 있다.
- **두 가지 실행 방식.** 같은 에이전트 정의를 Hermes 칸반 기반 실행과 Python 검증용 실행에서 함께 사용한다.
- **사람의 확인.** 발송·게시·일정 확정에 필요한 판단을 최종 결과에 표시해 오너가 검토할 수 있게 했다.

## 확장 계획

- Slack 게이트웨이를 연결해 메신저에서 칸반 카드를 등록하고 승인할 수 있게 한다.
- cron으로 매주 새 회의록이 있는지 확인하고, 새 회의록이 있으면 팀을 실행한다.
- Gmail·Notion MCP를 연결해 실제 고객 메일과 문서를 입력 자료로 사용할 수 있게 한다.
