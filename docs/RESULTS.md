# 시연 결과: 파비

## 무엇이 다른가

- **PM에게만 말하면 됩니다.** 요청을 정리하고, 직원을 배정하고, 결과를 모아 보고하는 일은 PM이 합니다. 사용자는 정리안을 승인하고 결과를 받습니다.
- **근거를 지어낼 수 없습니다.** PM이 자료에서 뽑은 근거마다 원문 인용이 붙고, 인용이 실제 자료에 없으면 프로그램이 받아들이지 않습니다.
- **검수를 통과한 문서만 받습니다.** QA가 정리안, 배정, 문서를 각각 검수하고, 통과하지 못하면 결과를 만들지 않습니다.

## 1. PM에게 한 말

> 파비 관련 자료 보낼게. 지금 두 가지 사업을 보고 있어. 하나는 정부지원사업에 낼 K-pop 한국어 교육 콘텐츠고, 하나는 아리랑TV랑 협업해서 파는 AI 굿즈야. 둘은 별개 사업이니까 섞지 말고, 각각 내부 검토용으로 뭘 만들어야 할지 정리해서 작업해줘.

PM은 자료로 충분히 판단할 수 있다고 보고 질문하지 않았습니다. 대신 세 가지를 직접 정하고 정리안에 적었습니다.

- 결과는 발표 자료가 아닌 내부 검토용 문서로 만든다.
- 정부지원사업은 특정 후보를 고르지 않고, 후보를 비교해 방향을 정할 수 있게 한다.
- 담당 직원은 정리안 단계에서 정하지 않고 작업 시작 때 배정한다.

## 3. PM이 정리한 업무

PM은 두 사업을 따로 나누고 문서 네 편을 정했습니다. 자료에서 근거 20개를 뽑아 상태별로 나눴습니다(결정 4, 제안 7, 미정 9).

| 사업 | 문서 | 검수 기준 예 |
| --- | --- | --- |
| 정부지원사업 교육 콘텐츠 | 공고 적합성 근거 검토 | 2026 공고 요건은 기존 자료의 주장으로 표시하고 공식 원문 확인 방법을 적는다. |
| | 교육 콘텐츠 후보 비교 | 가사, 방송, 아티스트 소재의 이용 권리는 확인 필요로 표시한다. |
| 아리랑TV 협업 AI 굿즈 | 제품 경험과 판매 가설 검토 | 매니저 방향은 선택됐지만 적용 범위와 동작은 미정으로 둔다. |
| | 협업과 판매 조건 확인표 | 녹음 재생과 합성 음성의 권리를 구분하고, 협의 결과를 지어내지 않는다. |

정리안 원본은 [목표](cases/pabi/pm/brief.md), [문서와 검수 기준](cases/pabi/pm/job.toml), [근거 20개](cases/pabi/pm/evidence.toml)입니다.

QA가 실제로 잡은 것은 다음과 같습니다.

- **정리안**: 검수 기준에는 공고 요건, 선정 사례, 방송 소재가 있는데 이를 뒷받침할 근거가 없었습니다. PM이 자료에서 해당 부분을 찾아 근거 네 개를 "미정" 상태로 추가했습니다. [QA 의견](cases/pabi/records/intake-review-1.json)
- **문서**: 투표·구독 혜택 문장에 다른 내용의 근거가 붙어 있었습니다. 마케팅이 맞는 근거로 바꿨습니다. [QA 의견](cases/pabi/records/review-1.json)

- 2027 지원사업 공고 원문을 확인한 뒤 교육 콘텐츠 후보의 우선순위를 정할지

결과 문서 미리보기 ([교육 콘텐츠 후보 비교](cases/pabi/outputs/grant-concepts.md)의 첫 부분):

```text
# tv파비 활용 K-pop 한국어 교육 콘텐츠 후보 비교

## 핵심 요약

- 우선 검증 방향은 가사·방송 원본 없이 자체 제작한 K-pop 주제 한국어 표현 학습이다.
  화면 시안으로 학습 흐름을 점검하고, 작동하는 시제품으로 7일 내 실제 재학습 행동을 관찰한다.
- 가사 활용은 기존 자료의 아이디어이고[e04], 실시간 방송 청취 방식에는 권리 검토가 필요하다[e09].
```

문장 끝의 `[e04]` 같은 표시는 [근거 파일](cases/pabi/pm/evidence.toml)의 근거 번호입니다.

## 테스트

### 자동 테스트 28개

실제 모델 대신 정해진 답을 돌려주는 가짜 모델을 넣고, 프로그램이 규칙대로 움직이는지 확인합니다. 코드를 고칠 때마다 다시 돌려 기존 동작이 깨지지 않았는지 봅니다.

```bash
python3 -m unittest discover -s hermes/tests
```

| 확인하는 것 | 예 |
| --- | --- |
| 근거를 지어내지 못한다 | 원문에 없는 인용, 다른 파일을 출처로 단 인용을 거부한다. |
| 승인 없이는 진행하지 않는다 | 사용자가 `n`을 입력하면 아무것도 저장하지 않는다. 같은 이름의 기존 정리안을 덮어쓰지 않는다. |
| PM과 QA가 정해진 만큼만 고친다 | QA 의견이 있으면 PM이 한 번 고치고, 남은 의견은 승인 화면에 표시한다. 사용자의 수정 요청은 세 번까지 받는다. |
| 직원은 필요한 자료만 받는다 | 다른 사업의 근거나 배정되지 않은 근거, 앞 문서의 전문은 받지 않고 요약만 받는다. |
| 검수를 통과해야 결과가 나온다 | 검수를 끝내 통과하지 못하거나 배정 검수가 해결되지 않으면 결과 문서를 만들지 않는다. |
| 고칠 때 필요한 문서만 다시 쓴다 | 수정된 문서와 그 문서를 이어받은 문서만 다시 쓰고 다시 검수한다. |
| 모델 응답 형식을 확인한다 | 필드가 빠진 응답, 키가 중복된 응답, 완료 기록이 없는 모델 호출을 거부한다. |
