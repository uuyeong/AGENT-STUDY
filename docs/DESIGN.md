# 설계: PM에게 말하면 일하는 AI 팀

사용자가 PM에게 하고 싶은 일을 말하고 자료를 넘기면, PM이 할 일을 정리하고 직원에게 나눠 줍니다. 각 직원이 문서를 쓰고, QA가 검수해 통과한 문서만 PM이 모아 사용자에게 돌려줍니다. 사용자는 PM하고만 이야기합니다.

```mermaid
flowchart LR
  U["사용자<br/>요청과 자료"] --> P1["PM<br/>질문하고 할 일 정리"]
  P1 --> C["사용자<br/>정리안 승인 또는 수정 요청"]
  C -->|"수정"| P1
  C -->|"승인"| P2["PM<br/>직원과 근거 배정"]
  P2 --> W["직원<br/>문서 작성"]
  W --> Q["QA<br/>검수"]
  Q -->|"수정 요청"| W
  Q -->|"통과"| R["PM<br/>결과 보고"]
  R --> U2["사용자<br/>결정과 다음 행동"]
```

## 직원

| 직원 | 하는 일 | 만드는 문서 예 |
| --- | --- | --- |
| PM | 사용자와 대화하고, 할 일과 담당을 정하고, 결과를 보고합니다. 종합 기획안을 직접 쓰기도 합니다. | 업무 정리안, 기획안, 결과 보고 |
| 제품기획 | 사용자 문제를 기능과 검증 기준으로 바꿉니다. | 기능 명세, 실험안 |
| 마케팅 | 누가, 왜 사는지 가설을 세우고 판매 메시지와 제휴 조건을 정리합니다. | 판매 포인트, 가격 실험, 제휴 질문 |
| 고객 응대 | 문의를 분류하고 정책에 근거한 답장 초안을 씁니다. | FAQ, 답장 초안 |
| 제작 | 기획을 바로 검토할 수 있는 콘텐츠로 만듭니다. | 교육 에피소드, 화면 문구, 대본 |
| QA | 정리안과 문서가 요청과 근거에 맞는지 검수하고, 문제가 있으면 고칠 점을 돌려보냅니다. | 검수 의견 |

직원마다 성격 파일(`agents/<직원>/SOUL.md`)과 작업 방법 파일(`agents/<직원>/SKILL.md`)이 있습니다. 직원은 일을 받을 때마다 이 두 파일을 함께 읽습니다.

## 직원끼리 일을 주고받는 방법

- **지시**: PM이 문서마다 "누가, 어떤 근거로, 무엇에 집중해서" 쓸지 정합니다.
- **인계**: 앞 문서가 있어야 쓸 수 있는 문서는 앞 문서의 핵심 요약(최대 네 줄)을 받습니다. 전문 대신 요약을 넘겨 입력을 줄입니다.
- **수정 요청**: QA가 문서 ID와 고칠 점을 적어 돌려보내면, 해당 문서를 쓴 직원과 그 문서를 이어받은 직원만 다시 씁니다.

직원끼리 직접 대화하지는 않습니다. 순서와 전달은 실행 프로그램(`hermes/intake.py`, `hermes/run_work.py`)이 맡고, 각 직원은 자기 차례에 필요한 자료만 받습니다.

## 요청부터 결과 문서까지

| 단계 | 누가 | 무엇을 | 남는 것 |
| --- | --- | --- | --- |
| 1. 요청 | 사용자 | 하고 싶은 일을 말하고 자료(.md, .txt)를 넘깁니다. | |
| 2. 질문 | PM | 자료로 알 수 없고 결과를 크게 바꾸는 것만 최대 세 개 묻습니다. 사용자가 무엇을 알고 싶은지 분명하지 않으면 그것부터 묻습니다. 답하지 않으면 PM이 정하고 가정으로 적습니다. | 대화 기록 |
| 3. 정리 | PM, QA | PM이 업무 정리안을 만듭니다. 사용자가 알고 싶은 질문, 질문마다 답할 문서와 검수 기준, 자료에서 뽑은 근거입니다. QA가 검수하고 PM이 한 번 고칩니다. | 정리안, 검수 의견 |
| 4. 승인 | 사용자 | 정리안 요약을 보고 승인하거나 고칠 점을 말합니다(최대 세 번). | `brief.md`, `job.toml`, `evidence.toml` |
| 5. 배정 | PM, QA | PM이 문서마다 담당 직원과 필요한 근거를 고릅니다. QA가 빠진 근거나 섞인 사업이 없는지 봅니다. | 배정표 |
| 6. 작성 | 직원 | 받은 근거와 앞 문서 요약으로 문서를 씁니다. 첫 줄에 맡은 질문에 대한 답과 추천을 씁니다. | 초안 |
| 7. 검수 | QA, 직원 | 질문에 답했는지부터 보고, 근거와 검수 기준을 확인합니다. 문제가 있는 문서만 최대 두 번 고칩니다. | 검수 기록 |
| 8. 결과 보고 | PM | 맨 앞에 PM 정리(사업별 판단, 맡긴 일, 결론)를 쓰고, 질문별 답, 문서 목록, 실행 기록을 붙입니다. 맡긴 일은 배정표에서 그대로 옮깁니다. | 결과 문서, PM 보고 |

### 근거란

자료에서 뽑은 한 줄짜리 내용입니다. 근거마다 출처 파일, 원문 그대로의 인용, 상태를 붙입니다. 상태는 다음 네 가지입니다.

| 상태 | 뜻 | 문서에서 쓰는 방식 |
| --- | --- | --- |
| 사실 `fact` | 자료가 확인한 내용 | 확인된 내용으로 씁니다. |
| 결정 `decision` | 사용자나 팀이 정한 내용 | 정해진 방향으로 씁니다. |
| 제안 `proposal` | 아이디어, 가설, 후보 | 검증할 대상으로 씁니다. |
| 미정 `open` | 아직 정해지지 않았거나 확인이 필요한 내용 | 확인 항목으로 남깁니다. |

## 결과를 믿을 수 있게 하는 장치

| 장치 | 내용 |
| --- | --- |
| 질문에 대한 답 먼저 | 모든 문서는 사용자의 질문 하나에 답하도록 만들고, 첫 줄에 답과 추천을 씁니다. 답 없이 미정 사항만 늘어놓으면 QA가 통과시키지 않습니다. |
| 인용 대조 | PM이 뽑은 근거의 인용이 실제 자료나 사용자의 말에 그대로 있는지 프로그램이 확인합니다. 없으면 받아들이지 않고 PM에게 다시 쓰게 합니다. |
| 사용자 승인 | 사용자가 정리안을 승인하기 전에는 저장하지도, 작업을 시작하지도 않습니다. |
| 정해진 순서 | 작업 순서와 수정 횟수는 프로그램이 정합니다. 어떤 직원도 검수를 건너뛸 수 없습니다. |
| 검수 통과 후 전달 | 검수를 끝내 통과하지 못하면 결과 문서를 만들지 않습니다. |
| 필요한 자료만 전달 | 직원은 자기 문서에 배정된 근거만 받습니다. 다른 사업의 자료는 받지 않습니다. |
| 외부 행동 금지 | 직원은 파일 작성만 합니다. 발송, 게시, 결제는 하지 않고 사용자 결정으로 남깁니다. |

## 사용 방법

### 실행

```bash
python3 hermes/intake.py <의뢰-이름> -s <자료 파일 또는 폴더> --run
```

| 옵션 | 쓰임 |
| --- | --- |
| `-s` | 넘길 자료입니다. `.md`, `.txt` 파일이나 폴더를 쓰며 합계 90KB까지 받습니다. |
| `-m "요청"` | 요청을 미리 적습니다. 생략하면 실행 후 입력합니다. |
| `--run` | 승인 후 바로 직원 작업까지 진행합니다. 빼면 정리안만 저장합니다. |
| `--skip-questions` | PM 질문 없이 가정으로 진행합니다. |
| `--yes` | 정리안 승인 없이 저장합니다. |
| `--model`, `--profile`, `--timeout` | 사용할 모델, Hermes 인증 프로필, 호출당 대기 시간(초)입니다. |

정리안만 저장했다면 나중에 `python3 hermes/run_work.py <의뢰-이름>`으로 직원 작업을 시작합니다. 모델 인증 상태는 `hermes -p default auth status openai-codex`로 확인합니다.

넘긴 자료는 OpenAI Codex에 전달됩니다. 외부에 보내도 되는 자료만 넘깁니다.

### 결과 폴더

모든 기록은 `hermes/jobs/<의뢰-이름>/`에 남고, 이 폴더는 Git에 올라가지 않습니다.

| 위치 | 내용 |
| --- | --- |
| `brief.md`, `job.toml`, `evidence.toml` | 승인된 정리안: 알고 싶은 질문과 목표, 만들 문서와 검수 기준, 근거 |
| `intake/<접수-id>/` | PM과의 대화, 정리안 초안, QA 의견, 사용량 |
| `runs/<실행-id>/delivery/` | 결과 문서와 PM 보고(`README.md`) |
| `runs/<실행-id>/overview.json` | PM 정리 원본 |
| `runs/<실행-id>/plan.json` | 문서별 담당과 근거 배정 |
| `runs/<실행-id>/drafts/`, `review-*.json` | 초안과 검수 의견 |
| `runs/<실행-id>/usage-summary.json`, `run.json` | 직원별 토큰 사용량과 진행 상태 |

### 문제가 생겼을 때

- **"이미 의뢰서가 있습니다"**: 같은 이름으로 다시 접수하면 기존 정리안을 덮어쓰지 않습니다. 다른 이름을 쓰거나 기존 폴더를 지웁니다.
- **검수를 통과하지 못함**: 결과 문서가 만들어지지 않습니다. `runs/<실행-id>/review-*.json`에서 지적 사항을 확인하고, 요청이나 자료를 보완해 다시 접수합니다.
- **모델 호출 실패**: `runs/<실행-id>/usage/`의 기록과 인증 상태를 확인합니다. 다시 실행하면 새 실행 폴더가 생깁니다.

## 기술 구성

| 구성 | 내용 |
| --- | --- |
| 모델 | OpenAI Codex `gpt-6-sol`. 모든 직원이 같은 모델을 쓰고, 성격 파일과 작업 지시로 역할을 나눕니다. |
| Hermes | 직원별 요청을 모델에 전달하고 응답과 토큰 사용량을 기록하는 명령줄 도구입니다. 도구 사용 없이 한 번씩 호출합니다. |
| `hermes/intake.py` | 사용자와 PM의 대화, 정리안 작성, 인용 대조, 승인 |
| `hermes/run_work.py` | 배정, 작성, 검수, 결과 보고 |
| `hermes/work_spec.py` | 정리안 파일의 형식 검사 |
| `hermes/tests/` | 가짜 모델로 위 규칙을 확인하는 자동 테스트 |

## 강의와의 연결

국민대학교 경영대학원 「AI에이전트실무」의 1~3주차 내용을 설계 기준으로 삼았습니다. 강의 PDF는 로컬 `lecture/` 폴더에 있습니다.

| 주차 | 적용 |
| --- | --- |
| 1주차 · 오케스트레이션과 결과 확인 | 사용자가 목표를 정하고, 결과는 근거와 검수 기록으로 확인합니다. |
| 2주차 · 프로필과 업무 위임 | 직원마다 성격 파일을 두고, 사용자는 PM에게만 위임합니다. |
| 3주차 · 스킬 | 직원마다 작업 방법 파일에 절차와 검증 기준을 둡니다. |
