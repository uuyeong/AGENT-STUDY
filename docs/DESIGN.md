# Hermes 실무 에이전트 설계

AGENT-STUDY는 사람이 정의한 의뢰를 여러 역할로 나눠 작성하고, 근거와 요구사항을 검수해 내부 납품하는 시스템이다. 제품 기획, 사업화, 고객 응대, 콘텐츠 제작처럼 성격이 다른 업무에 같은 실행기를 사용한다. 의뢰자가 정하는 **트랙**은 업무 범위다. 목표, 사용할 근거, 받을 산출물을 트랙별로 관리한다.

```mermaid
flowchart LR
  A["오너<br/>목표·트랙·완료 기준·가공 근거"] --> P["PM<br/>근거 분류와 담당 역할 배정"]
  P --> R["QA<br/>근거 귀속 검수"]
  R -->|"보완"| P
  R -->|"통과"| W["담당 역할<br/>트랙별 산출물 작성"]
  W --> Q["QA<br/>산출물별 검수"]
  Q -->|"보완"| W
  Q -->|"통과"| D["납품<br/>Markdown·CSV와 검수 기록"]
  D --> O["오너<br/>실행·제출·게시 결정"]
```

## 구성

| 경로 | 책임 |
| --- | --- |
| `agents/<역할>/SOUL.md` | 역할의 정체성, 판단 기준, 문체, 금지 사항 |
| `agents/<역할>/SKILL.md` | 작업 순서, 주의점, 산출물과 검증 방법 |
| `hermes/work_spec.py` | 의뢰 입력, 트랙과 산출물 ID, 출력 형식, 선행 관계 검증 |
| `hermes/run_work.py` | 역할별 프롬프트 조립, Hermes 호출, 근거 분류, 작성과 QA, 납품 |
| `hermes/submit_work.sh` | Hermes 칸반에 의뢰 접수. 카드의 초기 상태는 검토 대기다. |
| `hermes/setup_profiles.sh` · `hermes/TEAM.md` | 개별 칸반 워커용 프로필 설치와 협업 규칙 |
| `hermes/jobs/<의뢰-id>/` | 가공 입력, 독립된 실행 기록, QA 결과와 납품물 |
| `docs/` | 설계, 운영 절차, 검증 결과와 사례 자료 |

### Hermes와 LLM

| 항목 | 동작 |
| --- | --- |
| 에이전트 실행 환경 | Hermes CLI가 역할별 요청을 모델에 전달하고 응답과 사용 기록을 반환한다. Python 실행기가 입력, 선행 관계, QA 통과 여부와 파일 저장을 관리한다. |
| 모델 | 기본 제공자는 OpenAI Codex 계정 연결을 사용하는 `openai-codex`이며 기본 모델은 `gpt-6-sol`이다. 기본 인증 프로필은 Hermes의 `default`다. |
| 역할 구분 | PM, 작성 역할, QA는 각각 별도 호출이다. 동일한 기본 모델에 서로 다른 `SOUL.md`, `SKILL.md`, 단계별 지시와 입력을 제공한다. |
| 호출 방식 | `--safe-mode`, 빈 도구 목록과 일회 실행을 사용한다. 역할 파일과 필요한 의뢰 데이터는 실행기가 명시적으로 전달한다. |
| 인증과 검증 | 모델은 `--model`, 인증 프로필은 `--profile`로 지정할 수 있다. 실행기는 사용 기록의 제공자, 모델, 호출 횟수, 완료 여부를 확인한 응답만 채택한다. |

모델 설정과 실제 호출 결과는 각각 코드와 실행 기록으로 확인할 수 있다. [실행기](../hermes/run_work.py) · [실행 검증 결과](RESULTS.md)

## 역할

| 역할 | 판단과 작업 | 산출물 예시 |
| --- | --- | --- |
| PM `pm` | 전체 근거를 트랙에 배정하고 근거의 공유 이유와 귀속 보류 사유를 적는다. 산출물의 책임 역할과 형식을 지정한다. 의뢰에 따라 기획안을 통합한다. | `plan.json`, 기획안, 결정 메모 |
| 제품기획 `product` | 사용자 문제를 기능과 수용 기준으로 바꾼다. 앱·기기·운영 담당을 구분하고 예외 처리와 선행 조건을 적는다. | MVP 명세, 기능 검증표 |
| 마케팅 `marketing` | 고객군, 구매 이유, 판매 채널과 구독 가치를 가설로 세우고, 검증 지표와 제휴 확인 조건을 작성한다. | 판매 포인트, 가격 실험표, 제휴 안건 |
| 고객 응대 `client` | 문의를 분류하고 근거가 있는 답장과 운영 이관 기준을 정리한다. | FAQ, 답장 초안, 운영 개선표 |
| 제작 `producer` | 목적과 독자에 맞춰 콘텐츠를 바로 검토할 수 있는 형태로 만든다. | 교육 에피소드, 화면 문구, 대본 |
| QA `qa` | 작성 전에는 근거 귀속을, 작성 후에는 트랙별 근거·완료 기준·실행 가능성을 대조한다. 보완할 항목을 산출물 ID로 남긴다. | 분류 검수, 수정 요청, 최종 판정 |

각 산출물에 필요한 역할을 PM이 배정한다. 자료의 범위와 검수 기준은 오너가 정하고, 작업 결과의 외부 발송·제출·게시와 제품 결정은 오너가 승인한다.

## 실행과 납품

1. **입력 검증** — `brief.md`에 목표와 제약을, `job.toml`에 트랙·산출물·검수 기준을, `evidence.toml`에 사실·결정·제안·확인 대기 근거를 적는다. 실행기는 빈 입력, 중복 ID, 순환하거나 다른 트랙을 참조하는 선행 관계를 걸러낸다.
2. **분류와 선검수** — PM과 분류 QA는 전체 의뢰를 본다. 근거의 적용 범위가 모호하면 귀속을 보류한다. 분류 보완은 한 차례까지 가능하다.
3. **작성과 인계** — 담당 역할은 해당 트랙의 근거, 자기 산출물의 독자·목표·검수 조건, 요청서에 지정한 선행 산출물을 받는다. 예를 들어 기능 명세를 참조해야 하는 실험표는 기능 명세 뒤에 만든다. 문서에 포함된 지시문은 참고 데이터로 다룬다.
4. **형식 검증과 QA** — 실행기는 Markdown 제목과 CSV 머리글·행 구조를 확인한다. 트랙별 QA는 근거 연결, 완료 기준, 범위와 사실·가설 구분을 검토한다. 산출물 보완은 최대 두 차례이며, 선행 산출물을 수정하면 이를 사용하는 후속 산출물도 다시 작성한다.
5. **납품과 재실행** — 모든 산출물이 QA를 통과하면 `delivery/`에 납품 목록과 파일을 쓴다. 보류된 실행은 계획·초안·검수·사용 기록을 남긴다. 같은 의뢰를 실행할 때마다 별도 실행 폴더를 사용한다.

### 칸반에서 추적하는 방법

칸반 접수와 의뢰 실행은 별도 명령이다. `submit_work.sh`로 접수 카드를 생성하고, `run_work.py`로 작성·QA를 실행한다. 카드를 개별 Hermes 워커에 배정해 실행할 때는 `setup_profiles.sh`가 각 역할의 `SOUL.md`, `SKILL.md`, 칸반 규칙과 `agents/USER.md`의 오너 선호를 프로필에 설치한다. 실무 실행기는 저장소의 역할 파일을 직접 읽는다. [운영 절차](OPERATIONS.md) · [칸반 워커 규칙](../hermes/TEAM.md)

## 강의 계획과 설계 기준

국민대학교 경영대학원 「AI에이전트실무」의 강의 계획과 1~3주차 실습 자료를 참고했다. 실습은 도구 사용, 개인 에이전트 운영, 팀 운영, 산출물 공개의 순서로 구성된다. 이 프로젝트에서는 업무 분해, 사람과 에이전트의 책임, 결과의 검증 근거, 실패 후 복구를 설계 기준으로 삼는다. PDF는 `lecture/`에 있는 로컬 강의 자료에서 확인할 수 있다. [1주차 강의 계획 및 평가, 2~3쪽](../lecture/1주차.pdf#page=2)

| 강의 주제 | 설계에 적용한 내용 |
| --- | --- |
| 1주차 · 오케스트레이션과 결과 확인 | 오너가 목표와 완료 기준을 정의한다. Hermes와 실행기는 역할별 호출을 관리하고, 납품 결과는 입력·QA·모델 기록과 대조한다. 실패한 실행도 원인과 검수 상태를 확인할 수 있다. [1주차 자료, 29~30쪽](../lecture/1주차.pdf#page=29) |
